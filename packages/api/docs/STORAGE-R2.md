# Private file storage on Cloudflare R2

Last reviewed: 2026-11-07 against `main` @ `85ee822`. This is a plan. No bucket, account or token has been created, and no existing upload has been moved.

The API already has an S3-compatible storage driver (`src/services/storage/`). This document explains how it maps onto a private Cloudflare R2 bucket, what it costs, how to move existing local files without breaking anything, and how to recover from mistakes.

## 1. Architecture

### 1.1 Components

| Piece | File | Role |
|---|---|---|
| Driver interface | `src/services/storage/types.ts` | `put`, `get`, `delete`, `signedUrl`. `SIGNED_URL_TTL_SECONDS = 300`. |
| Driver factory | `src/services/storage/index.ts` | `STORAGE_DRIVER=local` (default) or `s3`. Validates the `S3_*` variables and refuses `local` in production unless `ALLOW_LOCAL_STORAGE_IN_PRODUCTION=true`. |
| S3 driver | `src/services/storage/s3.ts` | `@aws-sdk/client-s3`. Works with R2, AWS S3, Backblaze B2 and MinIO. Writes objects with `Cache-Control: private, no-store`. Flexible checksums are sent only when an operation requires them (`WHEN_REQUIRED`), which R2 needs. |
| Local driver | `src/services/storage/local.ts` | Disk under `<cwd>/uploads` (a temp directory under test). Atomic writes, content type kept in a `.storage-meta/` sidecar. |
| Key rules and local signing | `src/services/storage/signed-url.ts` | Strict key allow-list (`isValidStorageKey`), TTL bounds, HMAC-signed local URLs. |
| Upload helpers | `src/services/upload.service.ts` | `storeFile` / `readFile` / `removeFile` for delivery, drawing and instruction files. |
| Access checks for uploads | `src/services/file-access.service.ts` | `canAccessUploadedFile`: the key must belong to a record in the caller's company that the caller may view. |

`server.ts` exposes two decorators:

- `app.storage`: the driver from `getStorageDriver()`. Daily Report photos and PDFs use it.
- `app.uploadStorage`: delivery, drawing and instruction uploads. With `STORAGE_DRIVER=s3` it is **the same driver instance and bucket** as `app.storage`. With `local` it is a local driver rooted at the legacy upload directory, with the same layout as before.

### 1.2 Bucket

Use **one private R2 bucket per environment**, for example `constructos-prod` and `constructos-qa`. Never share a bucket between production and QA.

- No public access: do not enable the `r2.dev` public URL and do not attach a public custom domain.
- One R2 API token per environment, scoped to that one bucket, with **Object Read & Write** only. No account-level or admin token.
- Location hint next to the Railway region (for an EU-West Railway service: `WEUR`, or the EU jurisdiction if data residency is wanted).
- Encryption at rest is always on in R2. There is nothing to configure.

### 1.3 Key scheme (what the code writes today)

Keys are always generated by the server. No route accepts a storage key from a client for writing.

| Data | Key | Written by |
|---|---|---|
| Daily Report photo | `daily-reports/<companyId>/<reportId>/photos/<uuid>.jpg` | `daily-report.service.ts` (`addPhoto`) |
| Daily Report PDF | `daily-reports/<companyId>/<reportId>/rev-<revision>-<attemptId>.pdf` | `daily-report.service.ts` (`pdfKeyFor`) |
| Company logo for PDFs | `company.logoKey` (read only; nothing in the API writes it yet) | n/a |
| Delivery photo | `photos/<uuid><ext>` | `delivery.routes.ts` → `storeFile(..., 'photos')` |
| Delivery document | `documents/<uuid><ext>` | `delivery.routes.ts` → `storeFile(..., 'documents')` |
| Drawing revision | `drawings/<uuid><ext>` | `drawing.routes.ts` → `storeFile(..., 'drawings')` |
| Instruction attachment | `instructions/<uuid><ext>` | `instruction.routes.ts` → `storeFile(..., 'instructions')` |

Notes:

- **Only Daily Report keys carry a per-company prefix.** Delivery, drawing and instruction keys are `<type>/<random uuid><ext>` with no company segment. Their tenant boundary is enforced by the database lookup in `canAccessUploadedFile` (the key must match a row with the caller's `companyId`), not by the key layout. See §5.
- `<ext>` comes from the magic-byte-validated MIME type (`storedFileExtension`), never from the client file name.
- The two families cannot collide: legacy keys never start with `daily-reports/`.
- The database stores `fileKey` and, for legacy uploads, `fileUrl = /uploads/<fileKey>`. Neither contains a bucket name, host or driver, so the same rows work with either driver.

### 1.4 How files reach clients: presigned GET or streaming through the API

Every read starts with an API access check. What happens next depends on the data:

| Data | Access check | Delivery with `STORAGE_DRIVER=s3` | Delivery with `local` |
|---|---|---|---|
| Daily Report photos | Daily Report service (company, project, site, role) | **Presigned GET URL** for the R2 S3 endpoint, valid 300 s. The client loads it directly from R2 (`<img src>` / `<a href>`). | HMAC-signed `/api/v1/files/signed?...` URL, valid 300 s, served by `files.routes.ts`. |
| Daily Report PDF | Daily Report route and service | **Streamed through the API** (`storage.get` then `GET .../daily-reports/:id/pdf`). | Same. |
| Delivery, drawing, instruction files | `authenticate`, then a path guard, then `canAccessUploadedFile` on `GET /uploads/*` | **Streamed through the API** (`readFile`: bucket first, then the legacy local directory). | Same, from local disk. |

So the code supports **both** patterns today: presigned GET for Daily Report photos and API streaming for everything else. Legacy uploads are streamed rather than presigned because the web and mobile clients fetch `/uploads/<key>` with a Bearer token. Moving them to presigned URLs would need client changes (fetch a short-lived URL, then GET it without the token), so it is a separate, optional change.

Consequences:

- R2 egress is free, but bytes streamed through the API count as **Railway egress**. Presigned URLs avoid that.
- With presigned URLs loaded through `<img>` / `<a>`, no bucket CORS rule is needed. If a client ever uses `fetch()` on a presigned URL, add a bucket CORS rule allowing `GET` from the exact web origin only.
- Presigned URLs work only on the R2 S3 endpoint (`<account-id>.r2.cloudflarestorage.com`), not on a custom domain. That fits a private bucket.

## 2. Environment variables the driver reads

All are read in `src/utils/env.ts` and validated in `src/services/storage/index.ts`.

| Variable | Needed | R2 value | Notes |
|---|---|---|---|
| `STORAGE_DRIVER` | yes | `s3` | `local` (default) or `s3`. Any other value fails boot. |
| `S3_ENDPOINT` | yes for R2 | `https://<account-id>.r2.cloudflarestorage.com` | Must be an absolute URL, and https in production. Leave it empty only for AWS S3. Use the EU endpoint (`https://<account-id>.eu.r2.cloudflarestorage.com`) if the bucket was created in the EU jurisdiction. |
| `S3_BUCKET` | yes | the bucket name | |
| `S3_REGION` | yes | `auto` | |
| `S3_ACCESS_KEY_ID` | yes | the bucket-scoped token's access key ID | |
| `S3_SECRET_ACCESS_KEY` | yes | the token's secret | Secret variable. Never log or commit it. |
| `S3_FORCE_PATH_STYLE` | no | leave unset (`false`) | Only `true` or `false` is accepted. R2 does not need path style. |

If any of `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID` or `S3_SECRET_ACCESS_KEY` is missing, the driver throws a message naming the missing variables (not their values). The driver is created lazily, so the Daily Report and upload routes fail rather than the whole API boot.

Only relevant when **not** using R2:

- `FILE_URL_SECRET` (32+ characters): signs local-driver URLs. Required in production with `local`.
- `ALLOW_LOCAL_STORAGE_IN_PRODUCTION`: `true` only on a persistent volume.

`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` and `AWS_S3_BUCKET` are parsed by `env.ts` but nothing uses them. Do not set them.

## 3. Cost

### 3.1 Published R2 prices

Source: [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/), page last updated 2026-10-30, checked 2026-11-07. Re-check before committing to a budget.

| Item | Standard storage | Infrequent Access |
|---|---|---|
| Storage | **$0.015 per GB-month** | $0.01 per GB-month (30-day minimum) |
| Class A operations (writes, lists: `PutObject`, `ListObjects`, ...) | **$4.50 per million** | $9.00 per million |
| Class B operations (reads: `GetObject`, `HeadObject`, ...) | **$0.36 per million** | $0.90 per million |
| Data retrieval | none | $0.01 per GB |
| Egress | **free** | free |
| Free per month (Standard only) | **10 GB-month storage, 1 million Class A, 10 million Class B** | none |

`DeleteObject` is a free operation. Use Standard storage: site photos are read soon after upload, and Infrequent Access charges a retrieval fee and a 30-day minimum.

### 3.2 Worked estimate

Assumptions per active company (a pilot-sized customer of about 20 users on 2 to 3 sites):

- **Uploads:** about 50 files per working day (delivery photos and documents, drawings, instructions, Daily Report photos), 22 working days a month, about 1.5 MB average. That is about 1,100 objects and **1.7 GB of new data a month**.
- **Daily Report PDFs:** about 66 a month (3 sites x 22 days), about 1 MB each with revisions. Small next to photos, included in the operation count.
- **Class A:** about 1,200 PUTs a month.
- **Class B:** about 10,000 GETs a month (each view of a Daily Report loads every photo; PDF rendering reads each photo; file views are about 3x uploads).
- **Retention:** nothing is deleted in the first year, so storage grows linearly. Month 12 is the most expensive month of year one.
- One R2 account for all companies (the free tier is per account, not per company).

| Active companies | Stored at month 1 | Stored at month 12 | Class A / month | Class B / month | Cost at month 1 | Cost at month 12 |
|---|---|---|---|---|---|---|
| 10 | 17 GB | 204 GB | 12,000 (free) | 100,000 (free) | **about $0.11** | **about $2.91** |
| 50 | 85 GB | 1,020 GB | 60,000 (free) | 500,000 (free) | **about $1.13** | **about $15.15** |
| 200 | 340 GB | 4,080 GB | 240,000 (free) | 2,000,000 (free) | **about $4.95** | **about $61.05** |

Each cost is `(stored GB - 10 free GB) x $0.015`. Operations stay inside the free tier even at 200 companies.

Sensitivity:

- If operations were 10x the assumption at 200 companies (2.4 M Class A, 20 M Class B), add (2.4 - 1) x $4.50 + (20 - 10) x $0.36, which is **about $9.90 a month**.
- If average files were 3 MB instead of 1.5 MB, storage cost roughly doubles.
- Storage dominates. Image downscaling before upload is the biggest lever if cost ever matters.

**Not included:** Railway egress for bytes streamed through the API (legacy uploads and PDFs), and the optional backup copy (§7). Check Railway's current network pricing for the first; the second is cents per month at these sizes on a low-cost provider.

## 4. Moving from local disk to R2

### 4.1 What the code already does

With `STORAGE_DRIVER=s3`:

- **New files** of every kind go to the bucket.
- **Delivery, drawing and instruction files: dual-read is built in.** `readFile` tries the bucket, then the legacy local directory. A file that exists only on the old disk is still served until it is copied. `removeFile` deletes from the bucket and, best effort, from the legacy directory.
- **Daily Report photos and PDFs: no fallback.** They are read only from `app.storage`. Any Daily Report object that exists only on local disk returns "not found" after the switch until it is copied. Copy `daily-reports/` **before** switching, or accept that older Daily Report files are unavailable until the backfill finishes.
- **Database rows do not change.** `fileKey` is the object key in both drivers, and `fileUrl` stays `/uploads/<fileKey>`, which the API keeps serving. No migration and no URL rewrite are needed.

A Railway container's own disk is wiped on every redeploy. Files uploaded to a container without a persistent volume exist only until the next deploy. Copy them off before any deploy if they matter.

### 4.2 Backfill (design only; no script exists yet)

A one-off script, `packages/api/scripts/backfill-storage.ts` (proposed name), run by an operator with the production env:

1. **Inventory (read-only).** In a `BEGIN TRANSACTION READ ONLY` session, list every `fileKey` from `delivery_photos`, `delivery_documents`, `drawing_revisions`, `instruction_attachments`, `daily_report_photos`, and the `pdfFileKey` columns of `daily_report_revisions` and `daily_reports`, plus `companies.logoKey` where set. Record the count and total `fileSizeBytes` per table.
2. **Plan.** For each key, check that it passes `isValidStorageKey` and that the local file exists. Keys that fail the allow-list are not copied: the dual-read fallback keeps serving them from disk. List them for a decision. Write the plan (key, size, local SHA-256) to a local manifest file outside the repo.
3. **Copy.** For each key not already in the bucket (`HeadObject`), `PutObject` with the same key and the content type from the DB row (or the local sidecar). Skip `.storage-meta/`. The copy is idempotent, so the script can be re-run after a failure. Use a small concurrency limit (for example 4).
4. **Verify checksums.** Download each copied object (`GetObject`) and compare its SHA-256 with the manifest. `daily_report_photos.sha256` is an extra reference for Daily Report photos. Any mismatch is re-copied and reported. Never trust the S3 ETag as a checksum: it is not an MD5 for multipart uploads.
5. **Report.** Totals copied, skipped, already present, mismatched and missing locally. Exit non-zero if anything is mismatched or missing.
6. **Dry run first.** `--dry-run` performs steps 1 and 2 only, and `--verify-only` performs step 4 only.

The script never deletes local files and never writes to the database.

Simpler alternative for the pilot: `rclone copy uploads/ r2:<bucket>/ --exclude ".storage-meta/**" --checksum`, then `rclone check` and a comparison of the DB key list against `rclone lsf`. Keys are path-identical, so this works without a script.

### 4.3 Order of operations

1. Copy any files off the current container if it has no persistent volume.
2. Create the bucket and token (owner, §8). Set the `S3_*` variables on Railway with `STORAGE_DRIVER` still `local`.
3. Run the backfill dry run, then the copy and verification, against the current local files.
4. Set `STORAGE_DRIVER=s3` and redeploy.
5. Run the backfill once more to pick up files uploaded between steps 3 and 4, then verify again.
6. Smoke test as a normal user: open a delivery photo, a drawing revision, an instruction attachment, a Daily Report photo and a Daily Report PDF.

### 4.4 Rollback

- **Set `STORAGE_DRIVER=local` and redeploy.** The local directory is untouched by the backfill, so older files are still there if the disk persists.
- Files uploaded **while on R2** are only in the bucket. Before rolling back, copy them back: `rclone copy r2:<bucket>/ uploads/` (or the script in reverse).
- No database change is needed in either direction.
- Keep the local files (or the persistent volume) for at least one release after the switch before removing them.

## 5. Tenant isolation

- **No client-supplied keys.** Keys are built by the server from a fresh UUID plus server-side IDs. The `companyId` in Daily Report keys comes from the report row, which is scoped to the authenticated caller's company.
- **Every read is authorised first.** Daily Report reads go through the Daily Report service checks before a presigned URL is minted or a PDF is streamed. Legacy reads go through `canAccessUploadedFile`, which looks up the key together with the caller's `companyId` from the verified token.
- **Key validation.** `assertValidStorageKey` runs inside every driver call (`put`, `get`, `delete`, `signedUrl`). It is an allow-list: letters, digits, `.`, `_`, `-` and `/`, no empty, dot-leading or dot-trailing segments, no reserved device names, at most 512 characters.
- **Uniform not-found.** Denied and missing files return the same 404.
- **Credentials.** The bucket token never leaves the API. Clients only ever see a presigned URL for a single object, valid for 300 seconds.
- **Possible hardening (lead decision, not required for isolation):** prefix new legacy keys with `companies/<companyId>/` to allow per-company export, lifecycle and deletion by prefix. Existing rows would keep their keys, and the dual-read path already handles mixed layouts.

## 6. Signed URL lifetimes

| URL | TTL | Where set |
|---|---|---|
| Presigned R2 GET (Daily Report photos) | **300 seconds** | `SIGNED_URL_TTL_SECONDS` in `storage/types.ts` |
| Local signed URL (`/api/v1/files/signed`) | 300 seconds | same constant |
| Hard upper bound for any signed URL | 7 days | `MAX_SIGNED_URL_TTL_SECONDS` (R2 and SigV4 maximum) |

The API returns `urlExpiresAt` with each photo, and the web client refreshes the report before URLs expire. Keep the TTL short. A longer TTL only widens the window in which a forwarded link keeps working.

## 7. Recovery and backups

R2 does **not** keep previous object versions by default, so an overwrite or delete is final. The application never overwrites a key (every write uses a new UUID or attempt ID), so the main risks are deletes (application or operator) and token misuse.

- **Bucket lock rules** (R2 dashboard → bucket → Settings → Bucket lock rules, or `npx wrangler r2 bucket lock add <BUCKET_NAME> ...`) block delete and overwrite for a prefix, for an age, until a date or indefinitely. Bucket locks override lifecycle rules. Source: [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/) (updated 2026-10-28).
  - Do **not** lock everything: users legitimately delete photos and documents, and a lock would make those API deletes fail.
  - A reasonable pilot rule: lock `daily-reports/` for 30 days, since final PDFs should not disappear. Decide with the owner.
- **Lifecycle rules:** add one to abort incomplete multipart uploads after 1 day. Do not add expiry rules for business files without an agreed retention policy.
- **External backup:** a scheduled `rclone sync r2:<bucket> <backup-remote>:<bucket>-backup --backup-dir <backup-remote>:<bucket>-deleted/<date>` (weekly for the pilot, daily later) to another provider or account. The `--backup-dir` keeps deleted and changed files, which stands in for versioning. Use a separate, read-only token for the source.
- **Database and files together:** a restore needs both. Note the backup times of the Railway Postgres backup and the bucket backup together, and restore to matching points.
- **Restore drill:** once before launch, restore a handful of objects from the backup into the QA bucket and open them through the app.

## 8. Owner steps (nothing here is automated)

1. Create a Cloudflare account (or use the existing one) and enable R2. This may require a payment method even within the free tier.
2. Create a private bucket per environment (for example `constructos-qa` first, then `constructos-prod`), with the location hint next to the Railway region. Leave public access and `r2.dev` off.
3. Create an R2 API token per bucket: **Object Read & Write**, that bucket only. Store the access key ID and secret only in the Railway variable store.
4. Add a lifecycle rule to abort incomplete multipart uploads after 1 day. Decide on bucket lock rules (§7).
5. On Railway (QA first), set `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION=auto`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`. Follow §4.3 to switch `STORAGE_DRIVER=s3`.
6. Set up the external backup and run the restore drill (§7).
